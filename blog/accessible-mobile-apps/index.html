Accessible Android Apps: A Practical WCAG 2.2 Guide

AppMaven Studio
Independent Android developer
Jan 20, 2026
6 min read

An estimated 1.3 billion people, about 16% of the world's population, experience a significant disability. Many of them use Android with TalkBack, Switch Access, large fonts or a keyboard. This guide covers what an Android developer can actually do in code to make an app work for them, how the current WCAG 2.2 rules map to Android, and how to test the result.

Why Accessibility Is Worth the Effort

The World Health Organization estimates that 1.3 billion people experience a significant disability today, and notes that the number is growing as people live longer. Android's own accessibility guidance lists the groups you are designing for: people with impaired vision, colour blindness, impaired hearing, impaired dexterity and cognitive disabilities.

The same fixes help everyone. Clear labels, larger touch targets, readable contrast and text that scales make an app easier to use on a bumpy bus, in bright sunlight or with one hand. If you publish on Google Play, the pre-launch report also runs automated accessibility tests on builds you upload to a release track, so many problems show up in Play Console even before users report them.

WCAG 2.2 and How It Maps to Android

The Web Content Accessibility Guidelines are written for web content, but their principles carry over to native apps. WCAG 2.2 became a W3C Recommendation on 5 October 2023 and is the current version. It adds nine success criteria to WCAG 2.1 and removes the obsolete 4.1.1 Parsing. Each criterion has a conformance level of A, AA or AAA, and AA is the usual target for an app.

Several of the new criteria matter on a phone:

  • 2.5.8 Target Size (Minimum), level AA: pointer targets of at least 24 by 24 CSS pixels, or enough spacing around smaller ones. The stricter 2.5.5 Target Size (Enhanced) asks for 44 by 44 CSS pixels and is level AAA.
  • 2.5.7 Dragging Movements, level AA: anything done by dragging must also be possible with a single pointer without dragging, unless dragging is essential.
  • 2.4.11 Focus Not Obscured (Minimum), level AA: a component that receives keyboard focus must not be entirely hidden by content you added, such as a sticky bottom bar.
  • 3.3.8 Accessible Authentication (Minimum), level AA: do not make people remember, solve or retype something to sign in unless you offer help, such as password manager support and paste.

Android has its own numbers on top of WCAG. The platform guidance recommends touch targets of at least 48dp by 48dp, and specific contrast ratios for text measured in sp. Use those as your Android targets and treat WCAG as the shared vocabulary for audits and reports.

1. Label Everything That Is Not Text

TalkBack reads Text composables automatically. Icons and images need a contentDescription, written as a localized string that describes the purpose, not the picture: 

IconButton(onClick = onShare) {
    Icon(
        imageVector = Icons.Filled.Share,
        contentDescription = stringResource(R.string.label_share)
    )
}
  • Describe the action: "Share" or "Submit", not "Submit button". Use the Role semantics property (for example Role.Button or Role.Switch) so TalkBack announces the type for you.
  • Skip decoration: pass contentDescription = null for purely decorative images and icons inside an already labelled control.
  • Keep labels unique in lists: each item in a LazyColumn should be distinguishable by its own content, such as a city name.
  • Group related content: wrap a row of avatar, name and date in a container with Modifier.semantics(mergeDescendants = true) {} so it is read as one item.
  • Mark headings: Modifier.semantics { heading() } lets screen reader users jump between sections.
  • Announce changes: mark snackbars and status messages with liveRegion = LiveRegionMode.Polite. Do not use live regions on content that updates constantly, such as countdown timers.
  • Explain non-obvious actions: onClickLabel and onLongClickLabel turn "Double tap to activate" into "Double tap to open this article".

The details are in the Compose semantics guide and Android's principles for improving app accessibility.

2. Make Touch Targets at Least 48dp

Material components such as Checkbox, RadioButton, Switch and Slider reserve a 48dp target when they are interactive. Custom controls need it set by hand. If an element must stay visually small, the Material 3 minimumInteractiveComponentSize() modifier reserves at least 48dp of layout space around it. Put it before any size modifier: 

Box(
    Modifier
        .clickable { onToggle() }
        .minimumInteractiveComponentSize()
        .size(24.dp)
)

Leave space between neighbouring targets so a slightly missed tap does not trigger the wrong action. For gestures, follow the spirit of 2.5.7: if a list supports swipe to dismiss or drag to reorder, expose the same action as a button or as a custom accessibility action with CustomAccessibilityAction, so TalkBack, Switch Access and Voice Access users can reach it.

3. Let Text Scale

Define every text size in sp. Since Android 14 users can scale fonts up to 200%, with a nonlinear curve so large text grows less than small text. Apps that use sp get this automatically, but layouts still break if they assume a fixed height.

  • Use sp for text and line height, and dp for padding and sizes. With nonlinear scaling, 4sp plus 20sp is not guaranteed to equal 24sp.
  • Avoid fixed heights on containers that hold text; let them grow or scroll.
  • Test at the maximum font size in Settings > Accessibility > Display size and text, and also with a larger display size.
  • Do not hardcode calculations based on Configuration.fontScale or scaledDensity; use TypedValue.applyDimension() to convert.

4. Contrast and Colour

Android recommends a contrast ratio of at least 4.5:1 for text smaller than 18sp, or bold text smaller than 14sp, and at least 3:1 for larger text. Check pairs with Accessibility Scanner or a contrast checker, including text placed over images and gradients.

Never use colour as the only signal. An error state should add an icon and a message, not just turn a field red; a chart should use labels or patterns as well as hues. Android Studio's Compose UI Check mode can preview a screen for different types of colour vision deficiency and flag low contrast in previews.

5. Focus, Order and Sign-In

  • Logical order: swipe through a screen with TalkBack and confirm the reading order matches the visual order. The pre-launch report flags traversal order problems under "Implementation".
  • Nothing hides the focused item: people using a keyboard or Switch Access move focus step by step. Make sure persistent bars, overlays and bottom sheets never cover the item that has focus.
  • Easy sign-in: allow paste and autofill in password and code fields so password managers work, in line with 3.3.8.
  • Pane titles: give custom sheets and panes a paneTitle so accessibility services can announce when they appear.

6. Test With Real Assistive Technology

Android's accessibility testing guide recommends combining four approaches: manual testing, analysis tools, automated tests and user testing.

Manual Testing

  • TalkBack: turn it on, open the app and swipe through every element. Check that each announcement explains the purpose, that main workflows can be completed, that every element is reachable and that temporary messages are read aloud.
  • Switch Access: assign volume down as "Next" and volume up as "Select". Confirm that only actionable items are highlighted, each only once, and that everything available through gestures is also available as a control or custom action.
  • Large text and display size: repeat key screens at the largest settings.

Analysis Tools

  • Accessibility Scanner on a device suggests fixes for labels, touch targets and contrast.
  • Compose UI Check in Android Studio audits previews before you run the app.
  • Pre-launch report on Google Play lists touch target size, low contrast, content labelling and implementation issues with screenshots.

Automated Checks in Compose Tests

Starting with Compose 1.8.0 you can run the Accessibility Test Framework, the engine behind Accessibility Scanner, inside UI tests. Add the ui-test-junit4-accessibility dependency, then enable the checks: 

@get:Rule
val composeTestRule = createAndroidComposeRule<ComponentActivity>()

@Test
fun settingsScreen_passesAccessibilityChecks() {
    composeTestRule.setContent { SettingsScreen() }
    composeTestRule.enableAccessibilityChecks()
    // Any action, such as performClick(), also runs the checks.
    composeTestRule.onRoot().tryPerformAccessibilityChecks()
}

The checks catch missing labels, low contrast, small touch targets and traversal order problems. They do not replace a session with TalkBack, and neither replaces feedback from people who rely on assistive technology every day.

Key Takeaways

  • Use WCAG 2.2 as the reference; on Android, aim for 48dp touch targets and sp-based text
  • Give icons and images a purpose-based contentDescription, and null for decoration
  • Use Compose semantics: Role, heading(), mergeDescendants and live regions
  • Meet 4.5:1 contrast for normal text and never rely on colour alone
  • Offer a non-drag alternative for every drag or swipe action
  • Test with TalkBack, Switch Access, maximum font size and automated accessibility checks
