Android App Performance in 2026: Vitals, Startup and Jank

AppMaven Studio
Independent Android developer
Jan 10, 2026
7 min read

Android performance work in 2026 has a clear target: Google Play publishes the exact thresholds it treats as bad behaviour, and Jetpack ships the tools to measure and fix them. This checklist goes from what Play measures, through startup, rendering, memory and battery, to the build settings that make a release faster and the 16 KB page size requirement for apps with native code.

1. Start With What Google Play Measures

Android vitals collects quality data from users who allow it and shows it in Play Console. The core vitals affect your app's visibility on Google Play, and an app that exceeds a bad behaviour threshold may get less visibility and a warning on its store listing. Play assesses the last 28 days of data.

  • User-perceived crash rate: 1.09% overall, 8% on any single phone model.
  • User-perceived ANR rate: 0.47% overall, 8% on any single phone model.
  • Excessive partial wake locks: 5% overall.
  • Memory usage and bitmap memory usage: thresholds depend on the device RAM tier and app state, and differ for apps and games. Together with the DEX code optimization check, these may affect store visibility starting February 2027.

Startup time is not a core vital, but Android vitals still flags excessive startup: a cold start of 5 seconds or longer, a warm start of 2 seconds or longer, or a hot start of 1.5 seconds or longer, measured as time to initial display (TTID). An ANR happens when the app does not respond to an input event within 5 seconds, or when a foreground BroadcastReceiver does not finish within 10 to 20 seconds. Google's ANR guide also notes that users generally start to perceive slowness beyond 100 to 200 ms.

2. Measure Before You Optimise

  • Macrobenchmark: the Macrobenchmark library measures real user journeys with StartupTimingMetric and FrameTimingMetric. Run it on a physical device, not an emulator, against a build that is non-debuggable and minified like your release.
  • Time to full display: call reportFullyDrawn(), or use ReportDrawnWhen in Compose, when the screen is actually usable. Without it, only TTID is reported.
  • Tracing: system traces in Android Studio or Perfetto show what the main thread is doing during startup and janky frames, including Compose recomposition, layout and draw slices.
  • JankStats: the JankStats library reports per-frame timing from real sessions, with UI state attached. By default it counts a frame as jank when it takes twice as long as the current refresh period. Remember that a frame lasts about 16.7 ms at 60 Hz but only 8.3 ms at 120 Hz.
  • Network Inspector: the old Network Profiler is now the Network Inspector under View > Tool Windows > App Inspection. It supports HttpsURLConnection and OkHttp, which covers Retrofit.
  • Power Profiler: the Power Profiler shows power per subsystem (CPU, display, WLAN, cellular and more) on Pixel 6 and later Pixel devices running Android 10 or higher. Other devices report battery-level data instead.
  • StrictMode: enable StrictMode in debug builds to catch accidental disk and network access on the main thread.
// app/build.gradle.kts: a release-like variant for benchmarks
buildTypes {
    getByName("release") {
        isMinifyEnabled = true
        isShrinkResources = true
        proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"))
    }
    create("benchmark") {
        initWith(getByName("release"))
        signingConfig = signingConfigs.getByName("debug")
    }
}

3. Ship Baseline Profiles and Turn On R8

Baseline Profiles list the code paths used at startup and in key journeys so ART can compile them ahead of time. Google reports that they improve code execution speed by about 30% from the first launch. Generate them with the Baseline Profile Gradle plugin and a Macrobenchmark test, and add a Startup Profile so R8 can lay out the DEX files for faster startup.

R8 removes unused code and resources, inlines and merges classes and shortens names. Google lists faster startup, lower memory use, better rendering and fewer ANRs as the result. In practice:

  • Set isMinifyEnabled = true and isShrinkResources = true for release, with proguard-android-optimize.txt, as in the snippet above. AGP 9.3 adds a simpler optimization { enable = true } block that does both.
  • R8 full mode is the default since AGP 8.0. Remove android.enableR8.fullMode=false from gradle.properties if an old project still has it.
  • Refine broad keep rules: the broadest rules are the ones that prevent the most optimisation.
  • Android vitals now checks DEX optimisation: apps with more than 10 MB of DEX code (50 MB for games) should reach at least 25% optimisation, obfuscation and shrinking.

4. Make Startup Cheap

  • Keep Application.onCreate() light: initialise only what the first screen needs and create the rest on first use.
  • Use App Startup: the App Startup library lets libraries share a single content provider instead of one each, and AppInitializer.getInstance(context).initializeComponent(...) lets you initialise a component lazily.
  • Defer non-critical UI: show the first screen with placeholder data, then load images and secondary content in the background.
  • Use the SplashScreen API: custom splash activities add time; Android 12 and later require the SplashScreen API, and the compat library backports it.

5. Keep the Main Thread Free and Frames Smooth

Move disk, network, database and heavy computation off the main thread with coroutines on Dispatchers.IO or Dispatchers.Default, launched from viewModelScope or a LaunchedEffect. Never do I/O inside a composable. For Compose, the performance best practices boil down to a short list:

  • Cache expensive work with remember(keys), or move it to the ViewModel.
  • Give lazy list items stable keys and a contentType for mixed lists.
  • Use derivedStateOf when a fast-changing state should only trigger recomposition when a derived value changes, such as "is the list scrolled".
  • Defer state reads with lambda modifiers such as offset { } and drawBehind { }, so scroll and animation changes skip composition.
  • Never write to state that has already been read in the same composition (backwards writes).
LazyColumn {
    items(
        items = notes,
        key = { note -> note.id },
        contentType = { note -> note.type }
    ) { note ->
        NoteRow(note)
    }
}

6. Memory

Memory is now a core vital, measured as anonymous RSS plus swap and as bitmap memory, with separate limits per device RAM tier and app state. On a 4 GB device, for example, the foreground threshold for apps is 2.00 GB. The practical rules are familiar:

  • Decode bitmaps at the size you display them, not at full camera resolution.
  • Release caches when the system calls onTrimMemory().
  • Avoid holding an Activity or View in long-lived objects, and cancel work tied to a screen when the screen goes away.
  • Run LeakCanary, Square's open-source memory leak detection library, in debug builds to catch leaks during development.

7. Battery and Background Work

Use WorkManager for work that must survive the app closing or the device restarting, such as syncing or uploading logs. It supports constraints like an unmetered network, an idle device or sufficient battery, and it respects Doze. Use coroutines for work that can stop when the user leaves, and keep exact alarms for real alarms. Batch network requests where you can: the Power Profiler documentation shows how many small requests and one large request produce different power signatures on the WLAN rail. Hold partial wake locks only as long as necessary, since excessive wake locks are a core vital.

8. Support 16 KB Page Sizes

Starting with Android 15, devices can use a 16 KB memory page size. According to the page size guide, all apps targeting Android 15 (API level 35) or higher must support 16 KB page sizes on 64-bit devices on Google Play, and starting February 1, 2027 you will not be able to release updates that do not.

  • Apps written only in Kotlin or Java, including all their libraries and SDKs, already support 16 KB devices.
  • If your app or any SDK ships .so files, check them in the APK Analyzer, which flags alignment problems.
  • AGP 8.5.1 or higher and NDK r28 or higher produce 16 KB aligned builds by default. NDK r27 and lower need the -Wl,-z,max-page-size=16384 and -Wl,-z,common-page-size=16384 linker flags.
  • Test on the 16 KB Android emulator system image and verify with zipalign -c -P 16 -v 4 app.apk.

Key Takeaways

  • Track the core vitals: crash rate under 1.09%, ANR rate under 0.47%, plus wake locks and memory
  • Android vitals flags cold starts of 5 s, warm starts of 2 s and hot starts of 1.5 s or longer
  • Measure with Macrobenchmark, traces and JankStats before changing code
  • Ship Baseline Profiles and a Startup Profile, and keep R8 enabled for release
  • Keep I/O off the main thread and follow the Compose basics: remember, keys, deferred reads
  • Use WorkManager for persistent background work and batch network calls
  • If you ship native code, make sure it is 16 KB aligned before February 1, 2027
